B. First look at MIMIC-IV

  1. 加载三张基础表：patients、admissions、transfers，并把时间列解析为 datetime。
  2. 选择示例患者：用 subject_id 过滤一名患者；理解性别、anchor_age、anchor_year 和去标识化时间锚点。
  3. 检查年龄分布：按 anchor_age 分组画图，解释为什么 91 岁处出现堆积。
  4. 查看全部住院：按 admittime 排序，理解“一人多次住院”，并画出每次入院—出院的时间线。
  5. 统计入院来源：对 admission_location 分组计数，注意统计的是住院次数而非独立患者数。
  6. 重建院内移动：选最早一次 hadm_id，读取其 transfers，观察 ED、普通病房和出院顺序。
  7. 识别含 ICU 的住院：先用 ICU careunit 找到相应 hadm_id，再取该住院的全部 transfer，画出完整路径。
  8. 回到 admission 层解释结局：检查入院类型、来源和 discharge location。可选扩展：更换 subject_id，观察并非每个患者每张表都有记录。

最关键的知识：ID 决定数据粒度

ID表示什么典型使用常见错误
subject_id一名去标识化患者跨住院追踪患者；按患者拆分训练/测试用它替代 hadm_id，把多次住院混在一起
hadm_id一次 hospital admission诊断、住院化验、处方、transfer认为所有 hosp 记录都必然有或属于当前 admission
stay_id一次合并后的 ICU encounter连接 chartevents 等 ICU 表把一次床位 transfer 当成一次独立 ICU stay
itemid某个测量/治疗概念连接 d_items 或 d_labitems直接按 label 连接，忽略重名或 fluid 差异
specimen_id一份检验标本识别同一次抽血/采样产生的多项化验把每个 lab row 都当成独立采样
建模时先写清楚 observation unit模型的一行究竟是一名患者、一次住院、一次 ICU stay，还是一个时间窗口？这个选择决定去重、标签、特征聚合和数据集切分方式。

表在哪里，以及为什么总有一张 d_ 表？

hosp：医院范围 EHR

  • 行政：patients、admissions、transfers
  • 收费编码：diagnoses/procedures ICD
  • 临床：labevents、microbiologyevents、omr
  • 用药：prescriptions、pharmacy、emar

icu：ICU 临床系统

  • encounter：icustays
  • 观察：chartevents、datetimeevents
  • 输入/输出：inputevents、outputevents
  • 治疗：procedureevents

关系型数据库会把“事件事实”和“概念说明”分开：主表保存紧凑、稳定的代码，字典表保存人类可读描述。这是 database normalisation。

事实表代码字典表正确连接键
diagnoses_icdicd_coded_icd_diagnosesicd_code + icd_version
procedures_icdicd_coded_icd_proceduresicd_code + icd_version
labeventsitemidd_labitemsitemid
chartevents / ICU eventsitemidd_itemsitemid

真实临床数据的四层质量检查

1 · dtype

“看起来像数字”不等于数值列

OMR 同一列还可能含 120/80，Pandas 因而读取为 object。先显式转换，并决定不可转换值如何处理。

2 · missingness

缺失通常不是随机噪声

医生往往只在有临床理由时测量。变量“是否被测量”本身可能携带病情信息，也可能带来选择偏差。

3 · outlier

IQR 只是筛查，不是判决

5 英寸身高很可能是录入错误；极端化验值却可能是真实危急状态。先回看单位、时间和同患者相邻记录。

4 · unit

单位错误可以制造“病情突变”

97.3 kg 与 214.5 lb 几乎相同。没有机器可读单位时，必须通过范围、同患者轨迹和换算关系核查。

重点与易错点

❌ 用绝对年份比较患者✓ 日期按患者独立偏移；同一患者内部时间间隔通常可用，患者之间绝对年份不可直接比较。
❌ 把 91 岁当成准确年龄✓ anchor_age=91 只说明患者超过 89 岁。
❌ 只用 icd_code 连接✓ 同时连接 icd_version，避免 ICD-9/10 语义错配。
❌ 用 label 当唯一键✓ 使用 MIMIC 保证唯一的 itemid；相似 label 可能对应不同 fluid 或概念。
❌ 把 ICD billing code 当入院时特征✓ 编码常在出院后生成；用于早期预测会泄漏未来信息。
❌ 把 prescriptions 当实际给药✓ prescription 是意图；精确给药应查看 eMAR/eMAR detail，配制/发药看 pharmacy。
❌ 连续相同 careunit 就去重✓ 可能是真实换床或物理位置变化；先看时间和 transfer 语义。
❌ 所有患者都应有每类数据✓ 缺失可能表示未检查、未进入 ICU、记录在另一 admission，或关联 ID 缺失。
❌ IQR 标记后直接删除✓ 标记只是调查入口；先区分真实临床极值、录入错误和单位错误。
❌ 随意 SELECT * 大表✓ 特别是 chartevents，先限定列、cohort、stay_id 和时间范围。
❌ 按 admission 拆训练/测试✓ 同一患者不同住院可能同时落入两侧；通常应按 subject_id 分组拆分。
❌ 将受限 MIMIC 数据交给商业 LLM✓ 课程明确禁止。可以讨论公开 schema 和虚构示例，不要上传受限查询结果或患者记录。

把 Tutorial 扩展成研究思维

1. 先定 index time

例如“入 ICU 后 6 小时预测 48 小时死亡”。只有 index time 之前已知的数据才能成为特征。

2. 先写 cohort SQL

先得到一行一个研究样本的 cohort 表，再分别聚合 labs、vitals、medications，最后连接。

3. 保存 provenance

记录数据版本、表、itemid、单位转换、时间窗口和排除规则，让特征可复现、可审计。

推荐的特征工程顺序

定义 cohort粒度 + 时间点
→
提取事件ID + 时间窗口
→
标准化dtype + units
→
聚合last / min / max / slope
→
切分group by patient
缺失指示变量也可能泄漏“是否测量”确实可能预测病情，但若测量发生在 index time 之后，它仍然是未来信息。任何特征都必须同时审查语义和时间。
